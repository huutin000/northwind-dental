## Request guard and Task 9/10 rules (owner decisions after the Task 9 review)
- Both POST routes (`/api/chat`, `/api/leads`) run `checkJsonPost` (lib/guard/requestGuard.ts) BEFORE any session is created: `Content-Type` must be exactly `application/json` (else 415), `Sec-Fetch-Site` must be `same-origin` or `none` when present (else 403), and `Origin` must match the request host (or the first `X-Forwarded-Host`) when present (else 403). A rejected request gets no `Set-Cookie` and reaches no limiter, provider or store. Reason (verified on a production build): without it another site could post a `text/plain` form that parses as JSON, plant a lead in a fresh session and replace the visitor's cookie. Consequence for Task 10 and every future client: ALWAYS send `Content-Type: application/json` and call the API from the same origin; a `fetch` with a string body and no header will be rejected with 415.
- Lead API budget (corrected after the Task 9 fix-pass review): the KV client timeout applies PER REQUEST, `list` makes two requests in a row (LRANGE then MGET) and the counter can add an EXPIRE repair. Worst cases with the KV down: POST about 8.1 s (counter up to 1.6 s + categorisation 4.5 s + lead store 2.0 s) under `maxDuration = 10`, leaving about 1.9 s of headroom; GET about 4 s. The lead store has no circuit breaker (the counter has one), so with the KV down every `/leads` load can pay that time: acceptable, noted. A single deadline covering all of `list` is the cleaner fix if it ever matters.
- Request guard and security headers: the guard rejects `Origin: null`. With `Referrer-Policy: no-referrer` a same-origin `fetch` POST is reported to send `Origin: null` (Fetch spec, from memory, unverified), which would make every legitimate request answer 403. The M6 security headers must therefore NOT use `no-referrer` (use `strict-origin-when-cross-origin`, the Next.js default), or the guard must allow `Origin: null` together with `Sec-Fetch-Site: same-origin`. A Host header with an explicit default port (`example.com:443`) or a self-hosted proxy that rewrites Host without `X-Forwarded-Host` would also get false 403s; the deploy target is Vercel.
- The 400 branch of the lead size pre-check is reachable with real input (an email of 248 Japanese letters plus control characters in name and note exceeds 4096 bytes), so it stays; the draft uses the longest category value ("booking") so the pre-check is a true upper bound.
- Lead-store failures log at most one `[kv] lead store failure: <kind>` line per 60 s (kind only). The 3-lead slot is NOT refunded when the store fails after the slot was consumed. A lead whose model summary does not fit the 4096-byte cap is saved without the summary; form data that does not fit is a 400 and costs no slot.
- Task 10 renders `name`, `note`, `createdAt` and `summary` as plain text only (no HTML injection) and must show a friendly message for the 503 "could not save" answer; GET never returns an error body (an empty list can also mean "store temporarily unavailable").

## Known limitation (accepted by the owner): date/time over-redaction
- `redactPII` treats any run of 9 or more digits with separators as a phone number, so dates, times and amounts are over-redacted. Example: "Can I come 2026-11-09 10:30?" reaches `retrieve` and the model as "Can I come [phone]:30?" (pinned by a test, not changed). Booking questions that carry a date plus a time lose that part. Over-redacting is preferred to leaking a phone number.
